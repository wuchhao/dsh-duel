# 代码改造审核 Checklist（源自 S7 连接池改造实战，2026-11-06）

> 适用场景：任何「修 bug / 性能改造 / 重构」后的代码审核。写和审必须异构（不同模型或不同人），审者默认立场：**不信任自查结论**。
>
> C 组（上线后效果实证）依赖生产日志与上线后窗口，在代码审核循环内无法完成；循环内审核应逐条写「本循环内无法实证」，不得用均值或猜测替代分位数实证。C 组由上线后的第三方复核。

## A. 改动本身

- [ ] **P0 扫描**：批量替换/重命名后全仓 grep 残留（如 `getgetS7Biz` 这类二次嵌套 typo），一次 NameError 可致接口静默失效
- [ ] **共享资源生命周期**：对象池/连接池的 `__exit__`/`close`/`finally` 是否会误关共享实例；用 `with` 的旧调用点逐一核对
- [ ] **锁范围**：每个锁的获取→释放路径画出来；找「持锁做 IO/sleep」的段；确认无反向获取路径（死锁环）
- [ ] **异常分类**：通信失败 / 数据错误 / 配置错误是否区分？数据错误不应触发重连/重试等重型恢复动作（R2 教训：`_dead` 捕获过宽 → 每轮无谓重连）
- [ ] **重试语义**：重试前是否重建资源？重试上限按失败类型区分了吗？主症状场景（如 TCP 通但读写超时）下实测一轮最坏耗时

## B. 验证方法（写报告前必须做）

- [ ] **stub 实测**：用 stub 模拟主症状场景（不是理想场景），实测最坏耗时/连接次数/重试次数，与改造前对比——「修了但没修透」只有实测才暴露（R1 教训：12s/6 建连没降反升）
- [ ] **探针验证自愈路径**：半开连接（本地标志健康+实际已死）→ 确认真的触发重建
- [ ] **回归用例鉴别力**：故意引入回归（如把新锁换成空锁）→ 用例必须 FAIL；恢复后 PASS。不能 FAIL 的用例没有鉴别力
- [ ] **自测覆盖真实路径**：不能只测簿记（池计数），至少一条真实打包/读写链路（P2-5 教训）
- [ ] **大日志统计必须 `grep -a`**：二进制字节会截断 grep，得出「只有 1 次告警」的假结论（三批教训，差点漏掉 165s 卡死）

## C. 上线后效果实证

- [ ] **前后窗口对照**：用断点时刻（三条独立证据交叉定位发布时间）切分前后等长窗口
- [ ] **分位数而非均值**：p50/p90/p99 + >阈值事件计数。均值变好但尾部恶化 = 用户体验恶化（本次：告警率 −64% 但 p90 ×3.9、>20s ×3.1）
- [ ] **跑掉的指标要有人验**：每轮「待观察」项建台账，下轮日志复核闭环（建议 4 的轮询频率恢复至今未验）
- [ ] **上游旁证**：用不含本次改动内容的独立日志（如 WMS API 日志）证伪「上游被拖坏」——只能证伪，不能证明
- [ ] **归因到成分**：抓最长一次卡顿窗口前后 N 分钟原文，统计期间各类请求量，找到排队来源（本次：3 分钟 5600 次监控请求抢锁）
- [ ] **警惕「瓶颈转移」**：旧指标清零 ≠ 目标达成。检查新瓶颈（本次：连接风暴→单连接排队），如实写「未达成」

## D. 遗留管理

- [ ] 每个未修项写明：原因 + 风险 + 触发条件（不是一句「低风险」）
- [ ] 静默失效点（吞异常、AttributeError 被外层吞）至少补 `logging.error` 让日志可见
- [ ] 新引入的折衷（如写周期最长持锁 27s）写明与目标线的关系和降级开关

## 教训速查

| 教训 | 一句话 |
|---|---|
| grep 截断 | 大日志统计必须 `grep -a`，否则被二进制字节骗 |
| 修了≠修透 | stub 实测主症状场景才算数 |
| 病因掩盖 | 修掉一层后暴露的真根因（监控 24rps 与控制同锁排队）才是下步重点 |
| 作者自查盲区 | 写周期竞态是审核抓的，不是自查 |
