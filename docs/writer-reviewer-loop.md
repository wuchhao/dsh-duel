# 编写-审核双模型循环 · 工作流规范

> 用于在 DSH（或任何多 agent 平台）配置「一个模型编写 + 一个模型审核」的自动化闭环。
> 配套文档：`docs/code-review-checklist.md`（审核逐条过）。

## 一、角色定义

### Writer（编写模型）
- 输入：需求/目标 + 现有代码
- 职责：改代码、写/扩自测、跑通自测、更新 CHANGELOG（若仓库存在）
- **禁止**：在交付物里写「我已验证没问题」「全 PASS 可信」等自查结论——这些不进交接物

### Reviewer（审核模型）
- 输入：**仅**代码 diff + 需求描述 + 本规范 + checklist
- 职责：独立验证，产出分级审核报告
- **禁止**：看 Writer 的自查陈述、对话历史、修改过程
- **必须有执行环境**：能跑 stub/探针/grep/语法检查（纯读代码的审核深度掉一档）

## 二、循环规则

```
Writer 交付 → Reviewer 审核分流:
  有 P0/P1 → 打回 Writer（附报告全文），Writer 必须逐项响应
  仅 P2/P3 → 记录台账，可进入人工终审
  无人为 P0/P1/P2 → 人工终审 → 上线
```

- 硬门禁：**P0/P1 清零才出循环**，不做「礼貌性通过」（默认 `blockOn = [P0, P1]`，部署可配置；配置放宽时 dsh-duel 会在启动时告警）
- 每轮打回时 Writer 输出「审核响应表」（逐项：处置/理由/验证），格式见本文第三节「Writer 响应表」模板
- 单次循环最多 `maxRounds` 轮（默认 3，总轮次上限）；到达上限仍有 P0/P1 → 升级人工仲裁

## 三、交接物模板

### Writer → Reviewer（交接包）
```markdown
## 需求/目标
<一句话目标 + 验收标准>

## 变更文件清单
- <path>: <变更摘要>

## diff
<完整 diff 或文件全文>

## 自测
<自测项清单 + 运行方式（Reviewer 会复跑）>
```
注意：**不含**「为什么这样改是对的」的论证——论证写进 CHANGELOG（若仓库存在）或 PR 描述，审核者不需要被说服，只需要被证据检验。

### Reviewer → Writer（审核报告）
```markdown
# <改造名> 审核报告（第 N 轮）

## 一、结论
<可上线 / 打回（列 P0/P1 编号）>

## 二、逐项核验
<对 checklist A/B 各条的核验记录，写明「我实测了什么、结果是什么」>

## 三、问题清单
| 编号 | 级别 | 问题 | 复现方式（stub/探针/实测数据） | 建议 |
|---|---|---|---|---|

## 四、遗留项
<未修项写明：原因 + 风险 + 触发条件>
```

### Writer 响应表（打回后）
```markdown
| 审核编号 | 处置 | 修改内容 | 验证方式 |
|---|---|---|---|
```

## 四、审核硬手法（Reviewer 必做，防「修了但没修透」）

1. **stub 实测主症状场景**：不是理想场景。改造前后的最坏耗时/连接数/重试次数都要实测数字
2. **回归用例鉴别力验证**：故意把新保护措施换成空实现 → 用例必须 FAIL；恢复 → PASS
3. **全仓残留扫描**：批量替换后 grep 旧名/typo 变体
4. **异常分类核对**：通信失败/数据错误/配置错误是否走了不同的恢复路径
5. **锁路径审计**：画锁获取顺序，确认无死锁环、无持锁 IO/sleep
6. **大日志统计加 `-a`**：防二进制截断出假结论
7. **效果实证看分位数**：p50/p90/p99 + 超阈值事件计数，均值变好尾部恶化 = 不达标

## 五、上线后闭环

- 每轮「待观察」项进台账，指定验证指标和复核时间点
- 效果分析由**未参与编写和审核的第三方**（人或第三个 agent）用生产日志做，结论如「目标未达成」照实写
- 瓶颈转移检查：旧指标清零后，找新瓶颈并如实报告

## 六、模型选型建议

- Writer 和 Reviewer **至少异构一个维度**：不同模型 > 同模型不同人格提示词
- 同一模型既写又审时对抗性弱（易自我共识）——观察到此现象时换异构组合
- Flash 档执行层适合按本规范+checklist 照单执行；深度取决于流程框架，把硬手法固化进 checklist 可拉平差距

## 七、落地说明（dsh-duel 实现）

- 审核者与编写者都是宿主子代理，执行环境（能跑 stub/探针/grep/测试）由宿主的子代理 preset 提供；插件无法替宿主强制工具集，但会在审核前后比对 diff，一旦发现审核者改动了工作区，本轮审核结论作废并升级人工。
- 隔离模式要求独立后端（默认 `spawn`，不继承父会话历史）；`reviewer.isolation: true` 时拒绝 `fork`，也绝不回退到 `fork`。
- 交付物（交接包 / 审核报告 / 响应表 / manifest）落在工作目录 `.dsh-duel/runs/<runId>/`，该目录排除在审核 diff 之外。
- 工具：`duel_run`（完整闭环）、`duel_review`（只审核当前 diff）。字段与默认值见 README「配置」。
